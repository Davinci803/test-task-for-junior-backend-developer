# Backlog: периодичность задач

## В чем заключается задание

Нужно доработать существующий backend-модуль трекера задач так, чтобы задачи могли быть периодическими и автоматически создавались по заданным правилам.  
Функционально требуется поддержать 4 типа периодичности:
- ежедневные (каждый `n`-й день),
- ежемесячные (в конкретное число месяца `1..30`),
- на конкретные даты,
- только четные или только нечетные дни месяца.

Ключевая цель тестового: не просто добавить новые поля, а спроектировать полноценную фичу с учетом edge cases, качества архитектурных решений, совместимости с текущим API и внятной документации допущений.

## Принятый подход для реализации

Рекомендуемый базовый вариант: гибрид с материализацией.
- Хранить правила периодичности отдельно (сущность schedule).
- На их основе создавать реальные экземпляры задач фоновым генератором.
- Существующий CRUD задач оставить рабочим, не ломая текущие эндпоинты.

Почему это лучше для данного проекта:
- соответствует формулировке ТЗ "задачи создавались с учетом настроек";
- для пользователей проще работать с уже созданными задачами;
- уменьшает сложность "виртуальной" логики при чтении списка задач.

## Контекст текущего проекта (куда встраиваем изменения)

- Точка входа и wiring: `cmd/api/main.go`.
- HTTP маршруты и handlers: `internal/transport/http/router.go`, `internal/transport/http/handlers/task_handler.go`.
- Бизнес-логика задач: `internal/usecase/task/service.go`, `internal/usecase/task/ports.go`.
- Домен задачи: `internal/domain/task/task.go`.
- Репозиторий Postgres: `internal/repository/postgres/task_repository.go`.
- Текущая схема БД: `migrations/0001_create_tasks.up.sql`.
- API-контракт: `internal/transport/http/docs/openapi.json`.

## P0 (обязательно для сдачи)

### P0.1 Спроектировать модель периодичности и миграции БД

**Цель**  
Добавить хранение правил периодичности и связь с задачами без поломки текущей схемы.

**Что сделать**
- Добавить новую таблицу для правил периодичности (например `task_schedules`) с полями:
  - `id`, `base_title`, `base_description`, `status_template`,
  - `schedule_type` (`daily`, `monthly_day`, `specific_dates`, `odd_even_days`),
  - `schedule_payload` (JSON с параметрами правила),
  - `start_date`, `end_date` (nullable), `is_active`,
  - `created_at`, `updated_at`.
- Добавить в `tasks` ссылку на правило (`schedule_id`, nullable) и дату, на которую материализована задача (`planned_for`, date).
- Добавить уникальность, защищающую от дублей генерации (например уникальный индекс `(schedule_id, planned_for)`).
- Подготовить SQL-миграцию `migrations/0002_*.sql`.

**Definition of Done**
- Новая схема поднимается через Docker Compose с чистого volume.
- Миграция применима без конфликтов.
- Можно хранить все 4 типа периодичности.

**Edge cases**
- Некорректный JSON payload.
- Несовместимость `schedule_type` и payload (например `daily` без `interval`).
- `end_date < start_date`.

**Риски/зависимости**
- Нужно заранее определить формат payload, чтобы не ломать API позже.

### P0.2 Расширить домен и use case под периодичность

**Цель**  
Добавить предметные модели и валидацию правил периодичности.

**Что сделать**
- В домене создать сущность расписания (например `internal/domain/task/schedule.go`):
  - enum типов периодичности,
  - структуры параметров для каждого типа,
  - метод валидации.
- Зафиксировать календарную политику для месяцев разной длины (28/29/30/31):
  - для `monthly_day` хранить допустимые значения `1..30` (по ТЗ),
  - если в месяце нет целевого дня (например правило на 30-е в феврале), задача в этом месяце не создается,
  - поведение явно документировать в README и API-описании.
- В use case добавить контракты и сценарии:
  - создание/обновление/деактивация расписания,
  - расчет дат генерации задач в окне планирования,
  - идемпотентная генерация задач.
- Обновить `internal/usecase/task/ports.go`:
  - отдельный репозиторий расписаний,
  - методы batch-create задач для генератора.
- Сформулировать доменные ошибки (`ErrInvalidSchedule`, `ErrScheduleNotFound` и т.д.).

**Definition of Done**
- Логика валидации покрывает все типы периодичности.
- Use case API позволяет запускать генерацию независимо от HTTP слоя.
- Ошибки стабильно маппятся на корректные HTTP-коды.
- Календарное поведение для месяцев с разным количеством дней зафиксировано и покрыто тестами.

**Edge cases**
- `daily`: `interval <= 0`.
- `monthly_day`: значения вне `1..30`.
- `specific_dates`: пустой список, дубликаты, даты в прошлом.
- `odd_even_days`: запрещенные значения кроме `odd/even`.

**Риски/зависимости**
- Нужно зафиксировать timezone-стратегию на уровне use case (например UTC + date-only правила).

### P0.3 Добавить API для управления периодичностью

**Цель**  
Дать пользователю возможность задавать правила периодичности через HTTP API.

**Что сделать**
- Добавить эндпоинты (пример):
  - `POST /api/v1/schedules` — создать правило,
  - `GET /api/v1/schedules` — список правил,
  - `GET /api/v1/schedules/{id}` — детально,
  - `PUT /api/v1/schedules/{id}` — обновить,
  - `DELETE /api/v1/schedules/{id}` — деактивировать.
- Обновить роутинг в `internal/transport/http/router.go`.
- Добавить handler (например `internal/transport/http/handlers/schedule_handler.go`).
- Унифицировать DTO запросов/ответов и валидацию.
- Определить, создается ли "первая задача" сразу при создании расписания (рекомендуется: да, если дата подходит под правило).

**Definition of Done**
- Новые эндпоинты доступны и валидируют входные данные.
- Ошибки валидации возвращаются как `400`.
- Ответы согласованы по JSON-формату с существующим API.

**Edge cases**
- Неизвестные поля в JSON (должны отклоняться).
- Обновление активного расписания, уже имеющего сгенерированные задачи.
- Повторное удаление/деактивация.

**Риски/зависимости**
- Потребуется согласовать стратегию изменения уже сгенерированных задач при редактировании расписания.

### P0.4 Реализовать генератор периодических задач

**Цель**  
Автоматически материализовать задачи по правилам периодичности.

**Что сделать**
- Добавить компонент генерации (например `internal/usecase/task/schedule_generator.go`).
- Реализовать расчет дат генерации в окне (например на `today..today+N` дней).
- Явно реализовать правила для разной длины месяцев:
  - учитывать 28/29/30/31 день,
  - в високосный год корректно обрабатывать 29 февраля,
  - при отсутствии целевого числа в конкретном месяце не генерировать задачу за этот месяц.
- Добавить фоновый запуск из `cmd/api/main.go`:
  - ticker (например раз в сутки/час),
  - graceful shutdown вместе с HTTP сервером.
- Обеспечить идемпотентность:
  - проверка по уникальному индексу,
  - корректная обработка конфликтов вставки.

**Definition of Done**
- При активных правилах в БД появляются новые задачи в ожидаемые даты.
- Повторный запуск генератора не создает дубликаты.
- На выключение сервиса генератор завершается корректно.
- Для месяцев разной длины генерация ведет себя предсказуемо и соответствует задокументированной политике.

**Edge cases**
- Переход месяца для `monthly_day`.
- Февраль и короткие месяцы (правило на 30-е число).
- Високосный/невисокосный год для февраля.
- Переход с 31-дневного месяца на более короткий и обратно.
- Специфические даты за пределами окна генерации.

**Риски/зависимости**
- Без мониторинга генератор может "тихо" падать, нужен минимум логирования.

**Definition of Done**

**Риски/зависимости**

## Критерии готовности всей фичи

- Все 4 типа периодичности поддерживаются и валидируются.
- Периодические задачи реально создаются автоматически.
- Дубликатов от повторной генерации нет.
- API и OpenAPI обновлены, обратная совместимость не нарушена.
- Основные edge cases покрыты тестами.
- README содержит явные допущения и описание выбранных решений.
